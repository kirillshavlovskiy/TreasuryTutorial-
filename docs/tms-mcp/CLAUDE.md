# TMS Finance MCP — how this project uses it

This file applies to everything under `docs/tms-mcp/`. It explains what the TMS Finance MCP
server is, how this project is allowed to use it, and where the full tool catalogue lives.

The full catalogue — every read-only tool, its parameters, and the forbidden mutating tools by
name — is [tools.md](tools.md). Do not hand-edit it; it is regenerated by `/fx-sync-mcp-tools`.
Project-wide rules live in [`.claude/rules/project/tms-mcp.md`](../../.claude/rules/project/tms-mcp.md)
and are always in context; this file has the fuller version plus the task-to-tool map.

## What this project is, again

`test-treasury-project` computes FX buffers, VaR, and swap overlays from **hardcoded** tables
(`CURRENCY_PARAMS` in `lib/fx-buffer.ts`). It calls the TMS Finance MCP server through the client
in `lib/treasury/mcp-client.ts`, which now backs a `withTreasuryClient` helper used by every call
site added after `letsdeel/treasury#14082` deployed. Call sites: `lib/treasury/fx-rates.ts`
(`fx_rate_lookup`, `list_central_bank_codes`), `lib/treasury/snapshot.ts`
(`investment_revenue_summary`, for Notional Pool balances), `lib/treasury/fx-order-blotter.ts`
(`fx_order_blotter_search`), `lib/treasury/fx-pl-inventory.ts` (`fx_pl_inventory_overview`,
`fx_pl_inventory_by_currency`), `lib/treasury/accounts.ts` (`get_financial_account`,
`search_financial_accounts_advanced`), and `lib/treasury/notional-pool.ts`
(`notional_pool_overview`, `notional_pool_daily_metrics`, `notional_pool_rate_snapshot`,
`notional_pool_rate_history`). Three open sprint items in `.claude/rules/project/context.md`
(live CIP-implied rates, NWC carry maximization, swap balance-sheet netting) are blocked on data
this MCP server can now provide — the connector functions above expose it; no consuming feature
has wired them into a screen yet.

## Hard rules

1. **Only call read-only tools.** `annotations.readOnlyHint: true` in the tool's own metadata is
   the ground truth; [tools.md](tools.md) already sorts every tool into "Read-only catalogue" or
   "Mutating tools — never call" so you never have to check that flag yourself. This project is
   an analytics sandbox — it never books, creates, edits, or deletes anything in Treasury.
   Source: `.claude/skills/README.md` → "We never change data in Treasury."
2. **The catalogue only documents read-only tools.** A mutating tool's name and required
   permission are listed (so you know it exists and is off-limits) but never its description or
   parameters — nowhere in `tools.md`, including "Deep reference". (A read-only tool's *own*
   description can still name a mutating tool's parameter in passing — see `tools.md` § "How to
   read this file" item 4 for why that's not the same thing.)
3. **All financial data access goes through this MCP** — never a direct query to a database this
   project doesn't own. Source: `.claude/rules/dept/department.md`.
4. **Never log a tool's response payload.** Account identifiers, balances, and counterparty data
   are RESTRICTED. They leave the process only as this app's own authenticated API response — not
   to logs, error messages, telemetry, URLs, or commit messages. Source:
   `.claude/rules/dept/compliance.md`, `.claude/skills/README.md`.
5. **A rate always carries an explicit date and provider.** No implicit "current rate". `fx_rate_lookup`
   returns `provider` per result (confirmed live since PR #14082) and accepts `date` — use both when
   the number is going into a stored calculation. `getTreasuryFxRatesForUser` in `lib/treasury/fx-rates.ts`
   surfaces `provider` on every row (normalized to `null` if the tool ever omits it) but does not
   accept or pass through `date` — it only ever asks for latest rates; see that file's own header
   comment for the stated scope. Source: `.claude/rules/div/standards.md`.
6. **Money math is `Decimal.js`, never native float** — including anything computed from a tool
   response. Source: `CLAUDE.md` → Financial Data Handling.
7. **Approval thresholds are a hard stop in code, not a warning.** If a value derived from a tool
   response would cross an FX position or VAR threshold in `.claude/rules/div/fx-hedging-policy.md`
   ($50M/$100M/$250M position, $5M/$10M/$20M VAR), the code path must refuse, not just log.

## Response conventions

Every tool shares these, so they are not repeated per tool in the catalogue:

- Envelope: a `summary` string plus, on some tools, a `followUp` hint. Both survive `fields`/`omit`
  projection.
- Projection: every tool accepts `fields` (allowlist) and `omit` (denylist), dotted-path, applied
  server-side — use these to shrink a large response instead of re-reading it after the fact.
- Pagination: cursor-based, `nextCursor` in the response and `afterCursor` in the next call.
- Errors: `parseToolResult` in `lib/treasury/mcp-client.ts:89` already turns a non-2xx/`isError`
  response, missing text, non-JSON text, or a schema mismatch into a typed `Error` with the tool
  name in the message. Match that shape rather than inventing a new one.

## Honest gap: how a NEW tool gets classified as read-only

`/fx-sync-mcp-tools`'s cheapest path pulls a tool's description and parameters from the live
session via `ToolSearch`. **`ToolSearch`'s result does not include `annotations.readOnlyHint`** —
only `description` and the JSON-Schema `parameters`. That flag is only visible by reading the
tool's own `metadata` object in a `treasury` checkout.

So: when a local `treasury` checkout is available (`--repo`, `TREASURY_REPO`, or the default
path), the sync uses it as the source of truth for the read-only/mutating split — exact, from the
real `annotations.readOnlyHint`. When no checkout is available (a clone of only this repo, per
the self-containment requirement in `.claude/rules/project/decisions.md`), a tool name the
catalogue has never seen before is placed in a new **"Unclassified — verify before calling"**
bucket, never assumed read-only. An already-catalogued tool keeps its last confirmed
classification. This is slower to fully populate without a `treasury` checkout, but it never
silently mis-classifies a mutating tool as safe — see `.claude/skills/fx-sync-mcp-tools/SKILL.md`
Step 3 for the exact procedure.

## Updating the catalogue

```bash
/fx-sync-mcp-tools
```

Incremental by default — only tool names the session sees that the name index doesn't already
have. `/fx-sync-mcp-tools --full` rebuilds the whole file. See
`.claude/rules/project/tms-mcp.md` for when this runs automatically.
